# Exercise 03: Implement Cross-Cloud Networking

**Type:** Independent
**Difficulty:** Intermediate
**Estimated Time:** 3-4 hours

## Objective

Design and implement a cross-cloud networking architecture that connects a VPC
in AWS to a VNet in Azure using site-to-site VPN. You will configure the
networking resources on both sides, establish the VPN tunnel, verify
connectivity, and document the architecture.

## Background

Cross-cloud networking is the foundation of any multi-cloud strategy. Without
reliable, secure, and performant connectivity between clouds, multi-cloud
remains a collection of isolated islands. The two primary approaches are:

1. **Site-to-site VPN**: Encrypted tunnels over the public internet. Lower
   cost, easier to set up, but subject to internet latency.
2. **Dedicated interconnect**: Physical connections (AWS Direct Connect, Azure
   ExpressRoute). Lower latency, higher bandwidth, but significantly more
   expensive and slower to provision.

This exercise focuses on VPN-based connectivity as it is accessible without
physical infrastructure.

## Instructions

### Step 1: Design the Network Architecture

Before writing any code, create a network diagram (ASCII art or a tool like
draw.io) that shows:

- AWS VPC CIDR: `10.1.0.0/16`
- Azure VNet CIDR: `10.2.0.0/16`
- AWS public subnet: `10.1.1.0/24` (availability zone a)
- AWS private subnet: `10.1.2.0/24` (availability zone a)
- Azure subnet 1: `10.2.1.0/24`
- Azure subnet 2: `10.2.2.0/24`
- VPN tunnel endpoints on both sides
- Route table entries that direct cross-cloud traffic through the VPN

Ensure there are NO overlapping CIDRs.

### Step 2: Implement AWS Side (Terraform)

Create `aws-network.tf` that provisions:

1. A VPC with the specified CIDR
2. Two subnets (public and private)
3. An Internet Gateway attached to the VPC
4. A Virtual Private Gateway (VGW)
5. A Customer Gateway resource pointing to the Azure VPN gateway public IP
   (use a placeholder initially)
6. A VPN Connection between the VGW and Customer Gateway
7. Route tables with routes pointing cross-cloud traffic (10.2.0.0/16) to the VGW

### Step 3: Implement Azure Side (Terraform)

Create `azure-network.tf` that provisions:

1. A Virtual Network with the specified CIDR
2. Two subnets
3. A GatewaySubnet (required for VPN Gateway, name must be exactly
   `GatewaySubnet`)
4. A Public IP address for the VPN Gateway
5. A Virtual Network Gateway configured for VPN
6. A Local Network Gateway representing the AWS VPN endpoint
7. A VPN Connection linking the Azure VPN Gateway to the AWS Local Network Gateway
8. Route tables directing cross-cloud traffic (10.1.0.0/16) through the VPN

### Step 4: Create Test Instances

In each cloud, create a small compute instance in a private/internal subnet:

- **AWS**: A `t3.micro` EC2 instance in the private subnet with a security
  group allowing ICMP and SSH from 10.2.0.0/16
- **Azure**: A `Standard_B1s` VM in subnet 2 with a network security group
  allowing ICMP and SSH from 10.1.0.0/16

### Step 5: Verify Connectivity

Document the steps to verify the VPN tunnel is operational:

1. Check AWS VPN tunnel status (should show two tunnels, at least one UP)
2. Check Azure VPN connection status (should show "Connected")
3. From the AWS instance, ping the Azure instance's private IP
4. From the Azure instance, ping the AWS instance's private IP
5. Measure round-trip latency with 100 ping packets

### Step 6: Document the Architecture

Create an `architecture.md` file that describes:

- The network topology
- IP addressing scheme
- Routing logic
- Security group / NSG rules
- Known limitations (single tunnel, no redundancy, internet-dependent latency)
- How to extend this to use BGP for dynamic routing

## Success Criteria

- [ ] Network diagram accurately represents the topology.
- [ ] Terraform configuration creates all required networking resources on
      both AWS and Azure without errors.
- [ ] VPN tunnel is established (both sides show connected/up status).
- [ ] Instances on both sides can ping each other across the VPN tunnel.
- [ ] Security groups / NSGs restrict traffic to only the cross-cloud CIDR
      ranges (no overly permissive rules).
- [ ] Architecture documentation is complete and accurate.
- [ ] You can explain the trade-offs of VPN vs dedicated interconnect for
      production workloads.

## Hints

<details>
<summary>Hint 1: AWS VPN tunnel configuration</summary>

When creating an AWS VPN Connection, you must specify two tunnels. AWS
assigns each tunnel an outside IP address. You need these IPs to configure
the Azure Local Network Gateway. If you do not have the Azure IP yet, use
a placeholder and plan to update it. The tunnel pre-shared keys can be
specified or auto-generated by AWS.

```hcl
resource "aws_vpn_connection" "to_azure" {
  vpn_gateway_id      = aws_vpn_gateway.main.id
  customer_gateway_id = aws_customer_gateway.azure.id
  type                = "ipsec.1"
  static_routes_only  = true

  tunnel1_preshared_key = "YourPreSharedKey123!"
}
```

</details>

<details>
<summary>Hint 2: Azure GatewaySubnet requirements</summary>

The Azure VPN Gateway MUST be placed in a subnet named exactly
`GatewaySubnet`. This subnet should be at least /27 in size and should not
have a Network Security Group attached. Create it within your VNet:

```hcl
resource "azurerm_subnet" "gateway" {
  name                 = "GatewaySubnet"
  resource_group_name  = azurerm_resource_group.main.name
  virtual_network_name = azurerm_virtual_network.main.name
  address_prefixes     = ["10.2.3.0/27"]
}
```

</details>

<details>
<summary>Hint 3: Firewall rules for cross-cloud traffic</summary>

Both AWS Security Groups and Azure NSGs are stateful, so you only need to
specify the allow rules for inbound traffic. Make sure to allow:

- ICMP (for ping tests)
- SSH (port 22) for management
- Any application ports your workload needs

Avoid using `0.0.0.0/0` as the source. Use the specific remote CIDR.

</details>

<details>
<summary>Hint 4: Troubleshooting the tunnel</summary>

If the tunnel does not come up, check:

1. Azure VPN Gateway provisioning takes 20-45 minutes. Do not rush.
2. The pre-shared keys must match on both sides.
3. AWS generates TWO tunnel IPs; Azure needs a Local Network Gateway for
   each tunnel if you want redundancy.
4. Check that the Azure VPN Gateway SKU supports the required tunnel
   throughput.
5. Ensure route tables on both sides direct traffic to the remote CIDR
   through the VPN gateway, not the internet gateway.

</details>
