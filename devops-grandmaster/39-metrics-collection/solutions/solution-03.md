# Solution 03: Write PromQL Queries for Common Scenarios

## Part A -- Infrastructure Queries

### 1. CPU Utilization Percentage

```promql
100 - (avg by (instance) (rate(node_cpu_seconds_total{mode="idle"}[5m])) * 100)
```

This subtracts the idle CPU fraction from 100. `rate()` computes the
per-second rate of CPU time spent idle over the last 5 minutes. Since all
modes (user, system, idle, iowait, etc.) sum to 1 core-second per
core-second, the idle fraction subtracted from 100 gives the busy percentage.

### 2. Memory Utilization Percentage

```promql
(1 - node_memory_MemAvailable_bytes / node_memory_MemTotal_bytes) * 100
```

`MemAvailable` includes free memory plus reclaimable caches and buffers. It
is a better measure of actual available memory than `MemFree`.

### 3. Disk Utilization Percentage

```promql
(1 - node_filesystem_avail_bytes{fstype!="tmpfs",mountpoint="/"} / node_filesystem_size_bytes{fstype!="tmpfs",mountpoint="/"}) * 100
```

The `fstype!="tmpfs"` filter excludes memory-backed tmpfs filesystems whose
size is misleading. Use `mountpoint="/"` for the root filesystem or remove
it to see all mount points.

### 4. Load Average Normalized by CPU Count

```promql
node_load1 / count by (instance) (node_cpu_seconds_total{mode="idle"})
```

A load average of 4.0 on a 4-CPU system means the system is exactly
fully utilized. Above 1.0 per CPU, processes are queuing.

### 5. Network Bandwidth (MB/s)

```promql
rate(node_network_receive_bytes_total{device="eth0"}[5m]) / 1024 / 1024
```

`rate()` gives bytes per second. Dividing by 1024 twice converts to
megabytes per second. Use `device="lo"` for loopback or check available
devices with `node_network_receive_bytes_total`.

## Part B -- Rate and Increase Queries

### 6. CPU System Mode Rate

```promql
rate(node_cpu_seconds_total{mode="system"}[5m])
```

This returns the per-second rate of CPU time spent in kernel/system mode.
Values near 1.0 mean a full CPU core is consumed by system calls.

### 7. Total Bytes Received in 1 Hour

```promql
increase(node_network_receive_bytes_total{device="eth0"}[1h])
```

`increase()` computes the total increase over the time window, unlike
`rate()` which normalizes to per-second. The result is in bytes.

### 8. Disk I/O Utilization

```promql
rate(node_disk_io_time_seconds_total[5m]) * 100
```

`node_disk_io_time_seconds_total` tracks the total time the disk spent
doing I/O. `rate()` gives the fraction of time per second, so multiplying
by 100 gives a percentage. Values near 100% mean the disk is saturated.

## Part C -- Aggregation Queries

### 9. Average CPU Utilization Across All Instances

```promql
avg(100 - (rate(node_cpu_seconds_total{mode="idle"}[5m]) * 100))
```

With a single instance, this is identical to the per-instance value. With
multiple instances, it gives the cluster-wide average.

### 10. Top Filesystem by Disk Usage

```promql
topk(1, (1 - node_filesystem_avail_bytes{fstype!="tmpfs"} / node_filesystem_size_bytes{fstype!="tmpfs"}) * 100)
```

`topk(1, ...)` returns the single highest value. Remove the `topk` wrapper
to see all filesystems sorted.

### 11. Total Network Bytes Across All Devices

```promql
sum(rate(node_network_receive_bytes_total[5m]))
```

This sums the receive rate across all network interfaces, including `lo`,
`eth0`, `docker0`, etc. Filter by device if you want specific interfaces.

## Part D -- Alerting Expressions

### 12. CPU Usage Above 80%

```promql
(100 - (avg by (instance) (rate(node_cpu_seconds_total{mode="idle"}[5m])) * 100)) > 80
```

This returns a series only when CPU usage exceeds 80%. In an alerting rule,
Prometheus fires the alert when any series is returned.

### 13. Memory Usage Above 90%

```promql
(1 - node_memory_MemAvailable_bytes / node_memory_MemTotal_bytes) * 100 > 90
```

### 14. Disk Usage Above 85%

```promql
(1 - node_filesystem_avail_bytes{fstype!="tmpfs",mountpoint="/"} / node_filesystem_size_bytes{fstype!="tmpfs",mountpoint="/"}) * 100 > 85
```

### 15. Target Down

```promql
up == 0
```

The `up` metric is automatically generated by Prometheus. It is `1` when
a scrape succeeds and `0` when it fails.

## Part E -- Bonus: Time-based Queries

### 16. Compare Current Memory to 1 Hour Ago

```promql
(node_memory_MemTotal_bytes - node_memory_MemAvailable_bytes)
  - (node_memory_MemTotal_bytes - node_memory_MemAvailable_bytes offset 1h)
```

A positive result means memory usage increased over the last hour. A
negative result means it decreased. The `offset` modifier shifts the query
back in time by the specified duration.

### 17. Predict Disk Full Time

```promql
predict_linear(node_filesystem_avail_bytes{fstype!="tmpfs",mountpoint="/"}[1h], 24*3600)
```

`predict_linear()` uses simple linear regression on the last 1 hour of data
to predict the value 24 hours from now. If the result is negative, the disk
will be full within 24 hours at the current rate of change. If positive,
there is enough space.

To get seconds until full:

```promql
node_filesystem_avail_bytes{fstype!="tmpfs",mountpoint="/"}
  / deriv(node_filesystem_avail_bytes{fstype!="tmpfs",mountpoint="/"}[1h])
  * -1
```

This divides the current available space by the rate of change (negative
because space is decreasing). The result is seconds until zero.

## Why It Works

### The idle metric pattern

CPU metrics in Prometheus are cumulative counters per mode (user, system,
idle, iowait, etc.). Since all modes together account for 100% of CPU time,
computing the idle rate and subtracting from 100 is the simplest way to get
utilization. The `avg by (instance)` groups the result per host.

### MemAvailable vs MemFree

`MemFree` is the memory not used at all. `MemAvailable` is an estimate of
how much memory is available for starting new applications without swapping.
It includes reclaimable page cache and slab memory. `MemAvailable` is
always >= `MemFree` and is the correct metric for capacity planning.

### rate vs increase vs irate

- `rate()` -- average per-second rate over the window. Good for dashboards.
- `increase()` -- total increase over the window. Good for "how many in
  the last hour."
- `irate()` -- instantaneous rate using only the last two data points.
  Good for detecting spikes but noisy for dashboards.

### predict_linear limitations

`predict_linear()` assumes a linear trend. If disk usage is growing
exponentially (e.g., log files), the prediction underestimates. If usage is
cyclical (daily patterns), the prediction is unreliable. Use it as a
rough estimate, not a precise forecast.

## Common Mistakes

- **Forgetting the time range vector.** `rate(http_requests_total)` without
  `[5m]` returns an error. `rate()` requires a range vector (a set of
  data points over a time window).

- **Using `rate()` on a Gauge.** `rate()` is designed for Counters. On a
  Gauge, use `delta()`, `deriv()`, or just read the value directly.

- **Including tmpfs in disk queries.** tmpfs is a memory-backed filesystem.
  Its size equals a fraction of RAM, not disk. Including it in disk usage
  dashboards produces misleading results.

- **Not using `by (instance)` for per-host queries.** Without grouping,
  Prometheus aggregates all instances into a single average. If one host
  is at 100% and another is at 0%, the average shows 50% -- hiding the
  problem.

- **Confusing `rate()` and `increase()`.** `rate()` normalizes to
  per-second. `increase()` gives the total over the window. For "requests
  per second," use `rate()`. For "requests in the last hour," use
  `increase()`.
