# Solution 01: Zero Trust vs Castle-and-Moat

## Part A: Compare the Two Models

| Security Control | Castle-and-Moat | Zero Trust | Why? |
|-----------------|-----------------|------------|------|
| Network perimeter firewall | Yes | Yes | Both use firewalls, but zero trust adds internal segmentation |
| Mutual authentication between services | No | Yes | Castle-and-moat trusts internal traffic implicitly |
| VPN required for internal access | Yes | No (replaced by identity-aware proxy) | Zero trust replaces VPN with per-request authentication |
| Least privilege per service | No | Yes | Castle-and-moat grants broad internal network access |
| Encrypted internal traffic | Rarely | Always (mTLS) | Zero trust assumes the network is hostile |
| Continuous identity verification | No | Yes | Castle-and-moat verifies once at the perimeter |
| Micro-segmentation | No | Yes | Zero trust isolates every service independently |
| Assume breach mentality | No | Yes | Castle-and-moat assumes the perimeter holds |

### Why This Works

The fundamental difference is the trust boundary. Castle-and-moat draws a hard line at the network perimeter -- everything inside is trusted, everything outside is untrusted. Zero trust eliminates this binary boundary entirely. Every request, regardless of origin, must prove its identity and authorization.

In the castle-and-moat model, once an attacker bypasses the perimeter (via VPN compromise, phishing, or a trusted insider), they have free reign over the internal network. The flat network architecture means lateral movement is trivial -- the attacker in the incident scanned from 10.0.5.12 to 10.0.10.50 without encountering a single security control.

Zero trust inverts this assumption. Even if an attacker compromises a service, they must authenticate for every subsequent connection. Each service only knows about the services it is authorized to communicate with. The attacker cannot scan the network because network policies and service mesh controls prevent unauthorized connections from even being attempted.

### Common Mistakes

- **Thinking zero trust is a product.** Zero trust is an architectural philosophy, not a single tool. You cannot "buy" zero trust.
- **Assuming zero trust means no firewalls.** Firewalls still exist, but they are one layer among many, not the sole line of defense.
- **Believing zero trust is all-or-nothing.** Organizations implement zero trust incrementally, starting with the most critical assets.
- **Confusing VPN replacement with zero trust.** BeyondCorp-style identity-aware proxies replace VPNs, but zero trust extends far beyond remote access.

## Part B: Analyze the Breach Scenario

| Attack Step | Zero Trust Violation | Zero Trust Control | Detection |
|------------|---------------------|-------------------|-----------|
| Phishing email opened | N/A (endpoint security) | Device posture assessment | EDR agent detects malware |
| Malware installed | Device trust not verified | Device certificate + posture check | Device fails posture check, blocked from network |
| VPN connection (inherited trust) | "Never trust, always verify" violated | Identity-aware proxy with continuous auth | Anomalous device behavior flagged |
| Internal network scan | Micro-segmentation absent | Network policies block unauthorized connections | Service mesh logs show connection attempts to unauthorized targets |
| Jenkins compromised | Least privilege violated | Jenkins runs with minimal service account, no database access | Falco detects unexpected process execution |
| Database credentials extracted | Secrets in env vars (no vault) | Dynamic secrets from Vault, no static credentials | Vault audit log shows unauthorized credential request |
| Data exfiltration | No egress controls | Egress policies block unauthorized external connections | DLP detects data patterns in outbound traffic |

### Why This Works

Each attack step relies on a security weakness that zero trust is specifically designed to address:

1. **Device trust**: Zero trust includes device posture assessment. The compromised laptop would fail device health checks (malware detected, untrusted certificate) and be denied network access entirely.

2. **Identity verification**: Even with VPN access, zero trust requires per-request authentication. The attacker would need valid credentials for each service, not just network access.

3. **Micro-segmentation**: The internal network scan would fail because network policies prevent the developer laptop from communicating with Jenkins, the database, or any service not explicitly authorized.

4. **Least privilege**: Jenkins would run with a service account that has no database access. Even if compromised, it cannot reach the database.

5. **Secrets management**: Database credentials would not be stored in environment variables. They would be dynamically generated by Vault with short TTLs and scoped permissions.

### Common Mistakes

- **Focusing only on prevention.** Zero trust is about detection and response too. Even if the attacker gets in, you need to detect and contain them quickly.
- **Ignoring device trust.** Many zero trust implementations focus on service-to-service but forget about endpoint security. The BeyondCorp model includes device posture as a first-class concept.
- **Assuming mTLS alone is sufficient.** mTLS authenticates the service identity, but you still need authorization policies to enforce least privilege.

## Part C: Zero Trust Alternative Timeline

```
ZERO TRUST INCIDENT TIMELINE:

09:15 - Phishing email opened
        DETECTION: EDR agent flags suspicious email attachment
        RESPONSE: Email quarantined, user notified, security team alerted
        OUTCOME: Attack stopped at Step 1

--- IF ATTACKER BYPASSES EDR (assume breach) ---

09:22 - Malware installed on developer laptop
        DETECTION: Device posture agent detects unauthorized software
        RESPONSE: Device flagged as non-compliant
        OUTCOME: Device certificate revoked, network access denied

--- IF ATTACKER SPOOFS DEVICE IDENTITY ---

10:05 - Attacker attempts to connect to internal network
        DETECTION: Identity-aware proxy requires device certificate + user auth + MFA
        RESPONSE: Authentication fails (no valid device cert + no MFA token)
        OUTCOME: Connection denied, security team alerted

--- IF ATTACKER HAS VALID CREDENTIALS ---

10:47 - Attacker attempts to scan internal network
        DETECTION: Network policies block connections to unauthorized services
        RESPONSE: Istio logs show 403 responses, anomaly detection alerts
        OUTCOME: Scan returns no results, security team investigates

--- IF ATTACKER TARGETS JENKINS DIRECTLY ---

11:00 - Attacker connects to Jenkins
        DETECTION: Service mesh requires mTLS with valid service account
        RESPONSE: Connection denied (developer laptop has no service account)
        OUTCOME: Access blocked, security team alerted

--- IF ATTACKER COMPROMISES JENKINS (worst case) ---

11:30 - Jenkins compromised
        DETECTION: Falco detects unexpected process, Istio shows anomalous traffic
        RESPONSE: Automatic certificate revocation, service isolation
        OUTCOME: Jenkins quarantined, blast radius limited to Jenkins only

11:35 - Attacker tries to reach database
        DETECTION: AuthorizationPolicy denies Jenkins -> Database connection
        RESPONSE: 403 logged, alert fired
        OUTCOME: Database unreachable from Jenkins

11:40 - Attacker tries to extract credentials
        DETECTION: No static credentials in environment variables
        RESPONSE: N/A (nothing to steal)
        OUTCOME: Attacker cannot obtain database access

ATTACK CONTAINED: Blast radius limited to Jenkins only
DATA EXFILTRATED: 0 records
TIME TO CONTAIN: < 5 minutes (automated)
```

### Why This Works

The zero trust timeline demonstrates the power of defense in depth. Even in the worst-case scenario where the attacker bypasses multiple controls, each subsequent step requires overcoming additional authentication and authorization barriers. The critical difference is:

- **Castle-and-moat**: One breach = total compromise (single point of failure)
- **Zero trust**: Each step requires a separate breach (multiple independent barriers)

The blast radius in zero trust is bounded by the authorization policies. Even a fully compromised Jenkins service cannot reach the database because the AuthorizationPolicy explicitly denies that connection. The attacker would need to separately compromise the API Gateway service account to reach the database, which requires a completely different set of credentials and certificates.

### Common Mistakes

- **Assuming zero trust prevents all breaches.** Zero trust limits blast radius and speeds detection. It does not make systems impenetrable.
- **Forgetting about the assume breach principle.** The goal is not to prevent all attacks but to ensure that when (not if) a breach occurs, the impact is minimal and detection is fast.
- **Overlooking automated response.** Manual incident response takes hours. Automated certificate revocation and policy enforcement take seconds.

## Key Takeaway

Zero trust is not about building higher walls -- it is about eliminating the concept of a "trusted" zone entirely. In castle-and-moat, a single breach gives the attacker the keys to the kingdom. In zero trust, every door requires its own key, and the locksmith is watching. The core principle "never trust, always verify" means that network location is irrelevant -- what matters is identity, authorization, and continuous verification.
