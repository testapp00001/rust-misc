# Solution 01: What Happens When You Run a Container?

## Part A: Break Down the Command

When you type `docker run hello-world`, Docker performs these six steps:

1. **Parse the command.** Docker CLI parses `hello-world` as the image name.
   Since no tag is specified, it defaults to `hello-world:latest`.

2. **Check local image cache.** Docker looks in its local image store for
   `hello-world:latest`. If found, it skips to step 4.

3. **Pull the image.** If the image is not found locally, Docker contacts
   the default registry (Docker Hub), downloads the image layer by layer,
   and stores it locally. You see: `Pulling from library/hello-world`.

4. **Create the container.** Docker creates a new writable layer on top
   of the read-only image. It assigns the container an ID, sets up
   networking, and configures storage. This is equivalent to
   `docker create hello-world`.

5. **Start the container.** Docker starts the container's main process
   (the `CMD` defined in the image). For `hello-world`, this is the
   `/hello` binary. This is equivalent to `docker start <id>`.

6. **Execute and exit.** The `/hello` binary runs, prints its message to
   stdout, and exits with code 0. Docker marks the container as `Exited (0)`.

**Why this matters:** Understanding that `docker run` is a composition of
pull + create + start lets you intervene at any step. For example, you can
`docker create` a container without starting it, or `docker start` a stopped
container without re-creating it.

## Part B: The Full Command Anatomy

The minimal command `docker run hello-world` has many implicit defaults:

| Implicit Option | Explicit Version | What It Does |
|----------------|-----------------|--------------|
| Tag `latest` | `docker run hello-world:latest` | Uses the latest tagged version |
| Auto-remove: false | `docker run --rm hello-world` | Container persists after exit |
| STDIN: closed | `docker run -i hello-world` | Keeps STDIN open |
| TTY: none | `docker run -t hello-world` | Allocates a pseudo-TTY |
| Detached: false | `docker run -d hello-world` | Runs in background |
| Random name | `docker run --name my-hello hello-world` | Assigns a human-readable name |
| Default network | `docker run --network bridge hello-world` | Uses the default bridge network |
| No port mapping | `docker run -p 8080:80 hello-world` | Maps host port to container port |

The fully explicit version of `docker run hello-world` is:

```bash
docker run \
  --name <auto-generated> \
  --network bridge \
  hello-world:latest
```

**Why this matters:** When something goes wrong, you need to know which
defaults Docker chose so you can override them.

## Part C: Image vs Container

**Analogy:** An image is like a recipe. A container is like a cake baked
from that recipe.

- You can bake many cakes from one recipe.
- Each cake is independent -- eating one does not affect the others.
- The recipe is read-only (you do not change the recipe when you eat a cake).
- Each cake can be decorated differently (containers have their own writable layer).

**Answers:**

1. **How many containers from one image?** As many as you want. There is
   no limit. Each gets its own writable layer and isolated filesystem.

2. **After running `docker run hello-world` twice, how many containers?**
   Two. Check with `docker ps -a`:

   ```
   CONTAINER ID   IMAGE         COMMAND   STATUS
   abc123         hello-world   "/hello"  Exited (0) 2 minutes ago
   def456         hello-world   "/hello"  Exited (0) 5 seconds ago
   ```

   Each `docker run` creates a NEW container, even with the same image.

3. **After running `docker run hello-world` twice, how many images?**
   One. The image is only pulled once. The second run uses the cached image.
   Check with `docker images`:

   ```
   REPOSITORY    TAG       IMAGE ID       CREATED        SIZE
   hello-world   latest    d2c94e258dcb   6 months ago   13.3kB
   ```

**Why this matters:** If you keep running `docker run` without removing
containers, you accumulate stopped containers that consume disk space.
Use `docker ps -a` to see them and `docker rm` to clean up.

## Part D: What If the Image Already Exists?

When the image is already cached locally, the execution flow changes:

1. **Parse the command.** (Same as before.)
2. **Check local image cache.** Found! Skip to step 4.
3. **~~Pull the image.~~** (Skipped -- already present.)
4. **Create the container.** (Same as before.)
5. **Start the container.** (Same as before.)
6. **Execute and exit.** (Same as before.)

The only difference is that step 3 (the pull) is skipped. This makes the
command much faster -- from seconds to milliseconds for small images.

You can force a fresh pull with `docker pull hello-world` before running,
or use `docker run --pull always hello-world` to always check for updates.

**Why this matters:** In production, you want predictable behavior. Using
`:latest` and relying on the cache means you might run different versions
on different machines. Pinning to a specific tag (like `hello-world:1.0`)
gives you control over which version runs.

## Common Mistakes to Avoid

- **Running `docker run` in a loop without `--rm` or `docker rm`.** Each
  run creates a new container. Over time, you accumulate hundreds of stopped
  containers eating disk space.

- **Assuming `docker run` always pulls.** It does not -- it uses the local
  cache. If you want the latest version, pull explicitly first.

- **Confusing image ID and container ID.** They look similar (both are
  SHA256 hashes) but refer to different things. An image is immutable; a
  container is a running (or stopped) instance of that image.
