## The Problem

Your database is running on a single server. One day, a disk fails at 3 AM. Your application is down. Users cannot log in, orders cannot be placed, and your team is scrambling to restore from backups. The restore takes 4 hours. You have lost 4 hours of data and 4 hours of uptime.

Replication solves this by maintaining copies of your data across multiple servers, so that when one fails, others can take over. But replication introduces its own complexities: consistency, lag, and conflicts.

---

## The Naive Way

**"Just copy the files every hour"**

```bash
# Cron job: copy database files every hour
0 * * * * pg_dump mydb | gzip > /backup/mydb_$(date +\%Y\%m\%d\%H).sql.gz
0 * * * * scp /backup/mydb_*.sql.gz replica-server:/backups/

# Restore on replica
gunzip -c /backups/mydb_2024010112.sql.gz | psql mydb
```

**Why this fails:**
- 1 hour of data loss on failure (RPO = 1 hour)
- Restore takes significant time (RTO = 30+ minutes)
- Not real-time replication
- Manual process prone to errors
- Application must be stopped for consistent backup
- Cannot handle write traffic on replica

**"Just use rsync"**

```bash
# Copy PostgreSQL data directory
rsync -avz /var/lib/postgresql/data/ replica-server:/var/lib/postgresql/data/
```

**Why this fails:**
- Data files are not consistent if database is running
- Cannot rsync a live database without corruption
- No transactional consistency guarantee

## The Right Way

### Synchronous vs Asynchronous Replication

```
ASYNCHRONOUS REPLICATION (default, faster):

  Client → Primary → Commit → Response to Client
                   ↓ (async)
                 Replica → Apply

  Pros: Fast writes, low latency
  Cons: Replica may lag, data loss possible on primary failure

SYNCHRONOUS REPLICATION (safer, slower):

  Client → Primary → Replica → Ack → Commit → Response
                   ↓
                 Replica → Apply

  Pros: Zero data loss (replica always has latest data)
  Cons: Higher latency, primary blocks if replica is down
```

### PostgreSQL Streaming Replication

**Physical Replication (binary-level copy):**

```sql
-- On PRIMARY server
-- postgresql.conf
wal_level = replica
max_wal_senders = 5
max_replication_slots = 5
synchronous_commit = on  -- or 'remote_apply' for sync replication

-- pg_hba.conf: allow replication connections
-- TYPE  DATABASE        USER            ADDRESS       METHOD
host    replication     replicator      0.0.0.0/0     md5

-- Create replication user
CREATE ROLE replicator WITH REPLICATION LOGIN PASSWORD 'secure_password';
```

```bash
# On REPLICA server
# Stop PostgreSQL, clear data directory
systemctl stop postgresql
rm -rf /var/lib/postgresql/16/main/*

# Take base backup from primary
pg_basebackup \
  -h primary-server \
  -D /var/lib/postgresql/16/main \
  -U replicator \
  -Fp -Xs -P -R

# -Fp = plain format
# -Xs = stream WAL during backup
# -P = show progress
# -R = create standby.signal and primary_conninfo

# Start replica
systemctl start postgresql
```

```bash
# postgresql.auto.conf on replica (auto-generated by -R flag)
primary_conninfo = 'host=primary-server port=5432 user=replicator password=secure_password'
```

**Logical Replication (row-level, selective):**

```sql
-- On PRIMARY: Create publication
CREATE PUBLICATION my_pub FOR TABLE users, orders;

-- Or publish everything
CREATE PUBLICATION my_pub FOR ALL TABLES;

-- On REPLICA: Create subscription
CREATE SUBSCRIPTION my_sub
    CONNECTION 'host=primary-server dbname=myapp user=replicator password=pass'
    PUBLICATION my_pub;

-- Check replication status
SELECT * FROM pg_stat_subscription;
SELECT * FROM pg_replication_slots;
```

**Physical vs Logical:**

| Feature              | Physical           | Logical            |
|----------------------|--------------------|--------------------|
| Replication unit     | Entire cluster     | Selected tables    |
| Version compatibility| Same major version | Same or different  |
| Write on replica     | No                 | Yes (with care)    |
| Cross-platform       | No                 | Yes                |
| DDL replication      | Automatic          | Manual             |
| Performance          | Faster             | Slightly slower    |

### MySQL Replication

```sql
-- On PRIMARY: my.cnf
[mysqld]
server-id = 1
log_bin = mysql-bin
binlog_format = ROW
gtid_mode = ON
enforce_gtid_consistency = ON

-- Create replication user
CREATE USER 'repl'@'%' IDENTIFIED BY 'secure_password';
GRANT REPLICATION SLAVE ON *.* TO 'repl'@'%';

-- On REPLICA: my.cnf
[mysqld]
server-id = 2
relay_log = relay-bin
read_only = ON
super_read_only = ON

-- On REPLICA: configure and start replication
CHANGE REPLICATION SOURCE TO
    SOURCE_HOST='primary-server',
    SOURCE_USER='repl',
    SOURCE_PASSWORD='secure_password',
    SOURCE_AUTO_POSITION=1;

START REPLICA;
SHOW REPLICA STATUS\G
```

### Multi-Master Replication

```
MULTI-MASTER SETUP:

  Client A → Node 1 (Primary for US) ────┐
                                         ├──→ Shared Data
  Client B → Node 2 (Primary for EU) ────┘

  Both nodes accept writes
  Both nodes replicate to each other
```

```sql
-- PostgreSQL: Bi-directional logical replication
-- Node 1 (US)
CREATE PUBLICATION node1_pub FOR ALL TABLES;
CREATE SUBSCRIPTION node1_sub
    CONNECTION 'host=node2 dbname=myapp user=replicator'
    PUBLICATION node2_pub;

-- Node 2 (EU)
CREATE PUBLICATION node2_pub FOR ALL TABLES;
CREATE SUBSCRIPTION node2_sub
    CONNECTION 'host=node1 dbname=myapp user=replicator'
    PUBLICATION node1_pub;
```

**WARNING:** Multi-master replication is dangerous without conflict resolution.

### Conflict Resolution

```
CONFLICT SCENARIO:

  Time 1: User updates name to "Alice" on Node 1
  Time 2: User updates name to "Bob" on Node 2
  Time 3: Replication delivers both changes

  What should the name be? "Alice" or "Bob"?
```

**Strategy 1: Last-Write-Wins (LWW)**

```sql
-- Add timestamp column to track updates
ALTER TABLE users ADD COLUMN updated_at TIMESTAMP DEFAULT NOW();

-- Conflict resolution: latest timestamp wins
-- This is built into PostgreSQL logical replication with:
-- conflict_resolution = 'last_update_wins' (PG 16+)
```

**Strategy 2: Vector Clocks**

```json
// Each node maintains a version vector
{
  "name": "Alice",
  "vector_clock": {
    "node1": 5,
    "node2": 3
  }
}

// On conflict, compare vectors:
// If vector_a > vector_b: a wins
// If vector_b > vector_a: b wins
// If neither dominates: CONFLICT (manual resolution needed)
```

**Strategy 3: Application-Level Resolution**

```python
def resolve_user_conflict(local_record, remote_record):
    """Custom conflict resolution logic."""

    # Rule 1: Admin changes always win
    if local_record.get('changed_by_admin'):
        return local_record
    if remote_record.get('changed_by_admin'):
        return remote_record

    # Rule 2: Later timestamp wins
    if local_record['updated_at'] > remote_record['updated_at']:
        return local_record
    return remote_record

    # Rule 3: For certain fields, merge instead of overwrite
    # e.g., tags = local_tags | remote_tags (union)
```

## The Production Way

### Monitoring Replication Health

```sql
-- PostgreSQL: Check replication lag
SELECT
    client_addr,
    state,
    sent_lsn,
    write_lsn,
    flush_lsn,
    replay_lsn,
    pg_wal_lsn_diff(sent_lsn, replay_lsn) AS replication_lag_bytes,
    pg_wal_lsn_diff(sent_lsn, replay_lsn) / 1024 / 1024 AS lag_mb
FROM pg_stat_replication;

-- Check replication slot health
SELECT
    slot_name,
    slot_type,
    active,
    pg_size_pretty(pg_wal_lsn_diff(pg_current_wal_lsn(), restart_lsn)) AS lag
FROM pg_replication_slots;

-- MySQL: Check replica lag
SHOW REPLICA STATUS\G
-- Key fields: Seconds_Behind_Source, Last_IO_Error, Last_SQL_Error
```

### Handling Replication Lag

```python
# Application-level: Read-after-write consistency
def create_order(user_id, order_data):
    # Write to primary
    result = primary_db.execute(
        "INSERT INTO orders (user_id, data) VALUES (%s, %s) RETURNING id",
        user_id, order_data
    )
    order_id = result.fetchone()[0]

    # Force read from primary for this user's next request
    # (because replica may not have the data yet)
    cache.set(f"read_from_primary:{user_id}", "true", ex=5)

    return order_id

def get_user_orders(user_id):
    # Check if we need to read from primary
    if cache.get(f"read_from_primary:{user_id}"):
        return primary_db.execute(
            "SELECT * FROM orders WHERE user_id = %s", user_id
        ).fetchall()

    # Otherwise, read from replica
    return replica_db.execute(
        "SELECT * FROM orders WHERE user_id = %s", user_id
    ).fetchall()
```

### Replication Slots (Prevent WAL Accumulation)

```sql
-- Create a replication slot (prevents primary from removing WAL
-- before replica has consumed it)
SELECT pg_create_physical_replication_slot('replica1_slot');

-- On replica: use the slot
-- postgresql.auto.conf
primary_conninfo = 'host=primary port=5432 user=replicator'
primary_slot_name = 'replica1_slot'

-- Monitor slot health (CRITICAL: inactive slots cause disk fill!)
SELECT
    slot_name,
    active,
    pg_size_pretty(pg_wal_lsn_diff(pg_current_wal_lsn(), restart_lsn)) AS retained_wal
FROM pg_replication_slots;
```

## Hands-On Lab

### Lab: Set Up PostgreSQL Streaming Replication

**Objective:** Configure a primary PostgreSQL server with one synchronous replica and one asynchronous replica.

**Prerequisites:** Docker, docker-compose

**Step 1: Create the cluster configuration**

```yaml
# docker-compose.yml
version: '3.8'

services:
  pg-primary:
    image: postgres:16
    container_name: pg-primary
    environment:
      POSTGRES_DB: myapp
      POSTGRES_USER: admin
      POSTGRES_PASSWORD: adminpass
    ports:
      - "5432:5432"
    volumes:
      - pg_primary:/var/lib/postgresql/data
      - ./primary-init.sh:/docker-entrypoint-initdb.d/init.sh
    command: >
      postgres
      -c wal_level=replica
      -c max_wal_senders=5
      -c max_replication_slots=5
      -c hot_standby=on
      -c synchronous_commit=remote_apply
      -c synchronous_standby_names='pg-sync-replica'

  pg-sync-replica:
    image: postgres:16
    container_name: pg-sync-replica
    environment:
      POSTGRES_PASSWORD: adminpass
    ports:
      - "5433:5432"
    volumes:
      - pg_sync:/var/lib/postgresql/data
      - ./replica-init.sh:/docker-entrypoint-initdb.d/init.sh
    depends_on:
      - pg-primary

  pg-async-replica:
    image: postgres:16
    container_name: pg-async-replica
    environment:
      POSTGRES_PASSWORD: adminpass
    ports:
      - "5434:5432"
    volumes:
      - pg_async:/var/lib/postgresql/data
      - ./replica-init.sh:/docker-entrypoint-initdb.d/init.sh
    depends_on:
      - pg-primary

volumes:
  pg_primary:
  pg_sync:
  pg_async:
```

**Step 2: Primary initialization script**

```bash
#!/bin/bash
# primary-init.sh

psql -v ON_ERROR_STOP=1 --username "$POSTGRES_USER" --dbname "$POSTGRES_DB" <<-EOSQL
    -- Create replication user
    CREATE ROLE replicator WITH REPLICATION LOGIN PASSWORD 'repl_pass';

    -- Allow replication connections
    -- Note: pg_hba.conf is managed differently in Docker

    -- Create sample tables
    CREATE TABLE orders (
        id SERIAL PRIMARY KEY,
        user_id INT NOT NULL,
        product VARCHAR(200),
        amount DECIMAL(10,2),
        status VARCHAR(50) DEFAULT 'pending',
        created_at TIMESTAMP DEFAULT NOW()
    );

    CREATE TABLE users (
        id SERIAL PRIMARY KEY,
        name VARCHAR(100),
        email VARCHAR(255) UNIQUE,
        created_at TIMESTAMP DEFAULT NOW()
    );

    -- Insert sample data
    INSERT INTO users (name, email)
    SELECT 'User ' || i, 'user' || i || '@example.com'
    FROM generate_series(1, 1000) AS i;

    INSERT INTO orders (user_id, product, amount)
    SELECT
        (random() * 999 + 1)::int,
        'Product ' || (random() * 50 + 1)::int,
        (random() * 500 + 10)::decimal(10,2)
    FROM generate_series(1, 5000) AS i;
EOSQL

# Update pg_hba.conf for replication
echo "host replication replicator 0.0.0.0/0 md5" >> /var/lib/postgresql/data/pg_hba.conf
echo "host all all 0.0.0.0/0 md5" >> /var/lib/postgresql/data/pg_hba.conf
```

**Step 3: Replica initialization script**

```bash
#!/bin/bash
# replica-init.sh

# Wait for primary to be ready
until pg_isready -h pg-primary -U replicator; do
    echo "Waiting for primary..."
    sleep 2
done

# Stop PostgreSQL to replace data directory
pg_ctl -D "$PGDATA" -m fast -w stop

# Clear data directory
rm -rf "$PGDATA"/*

# Take base backup
PGPASSWORD=repl_pass pg_basebackup \
    -h pg-primary \
    -D "$PGDATA" \
    -U replicator \
    -Fp -Xs -P -R

# Configure as replica
cat > "$PGDATA/postgresql.auto.conf" <<EOF
primary_conninfo = 'host=pg-primary port=5432 user=replicator password=repl_pass application_name=replica'
primary_slot_name = 'replica_slot'
EOF

# Create standby signal
touch "$PGDATA/standby.signal"

# Fix permissions
chown -R postgres:postgres "$PGDATA"
```

**Step 4: Run and verify**

```bash
# Start the cluster
docker-compose up -d

# Wait for initialization
sleep 15

# Create replication slots on primary
docker exec pg-primary psql -U admin -d myapp -c \
    "SELECT pg_create_physical_replication_slot('pg_sync_replica_slot');"
docker exec pg-primary psql -U admin -d myapp -c \
    "SELECT pg_create_physical_replication_slot('pg_async_replica_slot');"

# Verify replication status
docker exec pg-primary psql -U admin -d myapp -c \
    "SELECT client_addr, application_name, state, sync_state,
            sent_lsn, write_lsn, flush_lsn, replay_lsn
     FROM pg_stat_replication;"

# Test write on primary
docker exec pg-primary psql -U admin -d myapp -c \
    "INSERT INTO orders (user_id, product, amount) VALUES (1, 'Test Product', 99.99);"

# Verify on sync replica
docker exec pg-sync-replica psql -U admin -d myapp -c \
    "SELECT * FROM orders WHERE product = 'Test Product';"

# Verify on async replica
docker exec pg-async-replica psql -U admin -d myapp -c \
    "SELECT * FROM orders WHERE product = 'Test Product';"

# Measure replication lag
docker exec pg-primary psql -U admin -d myapp -c "
SELECT
    application_name,
    sync_state,
    pg_wal_lsn_diff(sent_lsn, replay_lsn) AS lag_bytes,
    pg_wal_lsn_diff(sent_lsn, replay_lsn) / 1024 AS lag_kb
FROM pg_stat_replication;"

# Test that replica is read-only
docker exec pg-sync-replica psql -U admin -d myapp -c \
    "INSERT INTO orders (user_id, product, amount) VALUES (2, 'Bad', 0);"
# Expected: ERROR: cannot execute INSERT in a read-only transaction
```

## Limitation

Replication protects against server failure, but it does not protect against:
- Accidental data deletion (DELETE without WHERE clause replicates to all nodes)
- Corrupt data that replicates everywhere
- Storage failures that affect all replicas simultaneously
- Ransomware that encrypts all accessible databases

You still need **backups** -- independent, point-in-time snapshots of your data that are stored separately from your live database cluster.
